# ADK 악용 방지·업로드 한도 설계안 (승인 필요)

> 보안 점검(2026-11-20)에서 확인된 문제 중, **DB 스키마나 API 계약이 바뀌어서 구현 전에 승인이 필요한 것**의 설계안이에요.
> 아직 구현하지 않았어요. 승인해 주시면 아래 "구현 순서"대로 만들고 테스트를 붙여요.

## 1. 가입 선물 50 ADK 반복 수령 (Medium)

### 문제
계정을 삭제하면 `AdkEntry`와 `User` 행이 같이 지워지고, 같은 구글 계정으로 다시 가입하면 새 `user.id`가 생겨서
`ref="signup"`의 유니크 제약(`user_id`+`ref`)이 다시 통과돼요. 가입 → 삭제 → 재가입을 반복하면 매번 50 ADK(≈ AI 리포트 7건,
또는 모의투자 가상 현금 50만 원)를 받아요. 삭제 API에는 속도 제한이 없어요.

### 설계안 A (추천): 지급 이력을 따로 남기는 테이블
```
bonus_claims
  id          PK
  kind        'signup'            -- 앞으로 다른 일회성 보너스에도 쓸 수 있게
  subject     CHAR(64)            -- HMAC-SHA256(google_sub, 서버 비밀값). 원문 sub 는 저장하지 않는다
  claimed_at  timestamp
  UNIQUE (kind, subject)
```
- 가입 선물은 `bonus_claims` 행 INSERT 와 `AdkEntry` INSERT 를 **한 트랜잭션**에서 하고, INSERT 가 유니크 제약에 걸리면
  선물을 주지 않아요. 동시 요청·재전송·재가입 모두 DB 유니크 제약 하나로 막혀서 멱등이고 원자적이에요.
- 계정 삭제는 `bonus_claims`를 지우지 않아요. 지우면 이 방어가 의미가 없어서요.
- 해시에 서버 비밀값(HMAC 키)을 섞어요. DB 가 유출돼도 구글 `sub`를 거꾸로 알아내기 어려워요.

### 개인정보 영향 (확인이 필요해요)
탈퇴한 사용자의 식별자 해시를 보관하게 돼요. 부정 이용 방지 목적의 보관이라는 점과 보관 기간을 개인정보처리방침에 적어야
해요(`frontend/src/config/legal.ts`의 PRIVACY 초안에 "부정 이용 방지를 위해 탈퇴 후 ○개월간 식별자 해시 보관" 항목 추가).
보관 기간 만료 후 삭제하는 정리 작업도 같이 만들어요. 기간과 문구는 법률 검토가 필요해요.

### 마이그레이션 계획
1. 새 테이블은 시작할 때 `SQLModel.metadata.create_all`로 자동 생성돼요(기존 테이블은 건드리지 않아요).
2. 기존 사용자 보호: 1회 백필 스크립트(`app/scripts/backfill_bonus_claims.py`)가 현재 `users`의 `google_sub`로 `signup`
   행을 만들어요. 이걸 안 하면 이미 가입한 사용자가 삭제 후 재가입할 때 한 번은 더 받아요.
3. 새 환경 변수는 필요 없어요(HMAC 키는 `JWT_SECRET` 에서 파생: `HMAC(JWT_SECRET, "bonus-claim")`). 단, `JWT_SECRET`을
   바꾸면 해시가 달라져서 이력이 무효가 돼요 → 별도 `BONUS_HASH_KEY`를 두는 안도 있어요(권장).
4. 롤백: 코드를 되돌려도 테이블은 남아 있고 무해해요.

### 한계 (정직하게)
구글 계정을 여러 개 만드는 건 막지 못해요. 이건 가입 선물 금액을 줄이거나, 선물을 첫 행동 뒤에 주거나, 휴대폰 인증 같은
비용이 드는 방법이 필요해요. 이번 안은 "같은 구글 계정의 반복"만 막아요.

### 대안
- B: 삭제 후 N일 안에 같은 `sub`로 재가입하면 선물 없음 → `users`에 `deleted_at` 소프트 삭제가 필요해서 더 복잡해요.
- C: 가입 선물을 줄이고(50 → 10) 퍼즐·출석으로 채우기 → 기능 변경이고 악용 근본 해결은 아니에요.

## 2. 퍼즐 보상 — 정답 검증 없음 (Medium)

### 문제
- `GET /api/learn/crosswords/{id}`가 **정답(`words[].answer`)까지 그대로 내려줘요.** 프론트가 정답 확인을 하는 구조라서, 서버는
  "풀었는지"를 알 수 없어요. `POST /api/me/puzzle-completions`는 클라이언트가 보낸 `revealed=false`와 15초 대기만 봐요.
- 열어 본 시각(`PuzzleOpenRecord`)은 처음 연 때만 남아서, 다음 날부터는 15초 조건이 이미 충족돼 있어요. 스크립트로
  하루 2회 × 20 ADK = 40 ADK를 풀지 않고 받을 수 있어요.

### 설계안 A (추천, 근본 해결): 서버가 정답을 검증
1. `GET /crosswords/{id}`에서 `answer`를 빼고 `answer_length`만 내려줘요 (**API 응답 변경**).
2. 새 `POST /api/learn/crosswords/{id}/check`: 사용자가 채운 칸을 보내면 서버가 칸별 맞고 틀림을 돌려줘요(프론트의 "확인"
   기능을 대체). 정답 전체를 알려주지 않아요.
3. 완료는 `POST /api/me/puzzle-completions`에 채운 칸을 같이 보내고, 서버가 전부 맞는지 검사한 뒤에만 보상 후보로 세요.
   "정답 보기(reveal)"는 서버가 정답을 내려주는 별도 호출(`POST …/reveal`)로 바꾸고, 쓰면 그 퍼즐은 보상에서 제외해요.
4. 푸는 데 걸린 시간 하한(단어 수 × 몇 초)을 **그날 처음 연 시각**(일 단위로 새로 기록) 기준으로 검사해요.
- 장점: 정답을 모르면 보상을 못 받아요. 단점: **프론트 낱말퀴즈 로직 수정이 필요**(정답 확인·힌트·정답 보기), 이미 내려보낸
  정답을 아는 사람(공개 데이터였으므로)은 퍼즐 목록의 정답을 알고 있어요 → 퍼즐을 새로 만들거나, 기존 퍼즐은 보상 대상에서
  빼는 선택이 필요해요.

### 설계안 B (가벼운 보완, 근본 해결 아님)
- 열어 본 시각을 **일 단위**로 기록(`PuzzleOpenRecord`에 `day` 칸 추가 또는 매일 갱신)하고, 시간 하한을 단어 수에 비례하게.
- 정답은 이미 공개라서 서버가 답을 받아 비교해도 스크립트를 막지 못해요. 보상 한도(하루 2회)가 사실상 방어선이에요.

### 보상 지급의 원자성·멱등성 (지금 상태, 변경 불필요)
`wallet_service.grant`가 `(user_id, ref)` 유니크 제약으로 같은 날 같은 번째 보상을 한 번만 줘요. 동시성 테스트
(`tests/test_concurrency.py`)로 12개 스레드가 동시에 요청해도 한 번만 지급됨을 확인했어요. 기록 갱신(`PuzzleCompletionRecord`)은
읽고-쓰는 방식이라 동시 요청에서 한쪽 기록이 덮여 **보상이 덜 쌓일 수는 있지만 더 쌓이지는 않아요**.

### 권장
먼저 **1번(가입 선물)**을 구현하고, 퍼즐은 A안을 프론트와 함께 진행하는 걸 권장해요(백엔드·프론트 PR 2개, 순서: 백엔드가 새 API
추가 → 프론트 전환 → 백엔드가 `answer` 제거). 전환 기간에는 둘 다 지원하는 호환 단계를 둘 수 있어요.

## 3. 업로드 — 사용자별 용량 한도 (Medium) · 구체 설계안 (DB 변경은 아직 안 함)

### 이미 한 것 (승인 없이 가능한 범위)
- 파일당 5MB 제한(기존), 사진 구조 검증, EXIF·텍스트 등 메타데이터 제거(회전 값만 유지), 사진 뒤에 덧붙은 데이터 제거(`image_clean.py`)
- 글·댓글 삭제·사진 교체 시 파일 삭제(다른 글이 같은 사진을 쓰면 유지), 고아 파일 정리 스크립트
- 사진 주소를 `PUBLIC_BASE_URL` 설정으로 만들기 (요청 Host 로 만들지 않음)

### 문제
사용자별 합계를 세려면 "누가 올렸는지"를 알아야 하는데, 지금은 파일 이름(uuid)만 있고 소유자가 어디에도 없어요. 로그인 사용자는
분당 10장까지 올릴 수 있어서, 한 계정이 하루 수십~수백 MB, 계정을 늘리면 디스크를 채울 수 있어요.

### 데이터 구조
```
uploads                              -- 새 테이블
  name        VARCHAR(40) PRIMARY KEY   -- "<uuid32>.<jpg|png|webp>" (디스크 파일 이름과 같다)
  user_id     INT NOT NULL REFERENCES users(id) ON DELETE CASCADE, INDEX
  size        INT NOT NULL              -- 정리(메타데이터 제거) 뒤의 실제 저장 바이트
  created_at  TIMESTAMPTZ NOT NULL, INDEX
  attached_at TIMESTAMPTZ NULL          -- 글·댓글에 처음 붙은 시각 (NULL = 아직 안 붙음)
```
- **소유권**: 올린 사람 = `uploads.user_id`. 글·댓글에 붙일 때 `check_image_url` 이 "내가 올린 파일인지"를 확인한다
  (지금은 이 서버에 있는 파일이면 누구 것이든 붙일 수 있다 → 남의 사진을 내 글에 붙이는 일도 막힌다).
  이미 다른 글에 쓰이는 파일을 같은 사용자가 두 글에 붙이는 건 허용(참조 확인 후 삭제).
- **한도**: 사용자별 저장 합계 ≤ **50MB**, 24시간 업로드 ≤ **30장**, "아직 안 붙은 사진" ≤ **10장**
  (붙이지 않고 올리기만 반복하는 걸 막는다). 값은 설정(`UPLOAD_USER_QUOTA_MB` 등)으로 뺀다. 초과하면 413(`UPLOAD_QUOTA_EXCEEDED`).
- **삭제 연동**: 글·댓글 삭제로 파일을 지우면 `uploads` 행도 지운다 → 합계가 줄어 다시 올릴 수 있다. 회원 탈퇴는 `ON DELETE CASCADE` +
  파일 삭제(지금 `account_service` 가 이미 파일을 지운다).
- **고아 정리**: `attached_at IS NULL AND created_at < now()-24h` 인 행과 파일을 지운다 (지금은 파일 시각과 글 참조로 추정, 이 구조가 되면
  소유자·시각이 정확해진다). 디스크에 있는데 `uploads` 에 없는 파일(= 기존 파일)은 현재 방식으로 계속 처리.

### 동시 업로드
한도 검사와 행 추가를 **한 트랜잭션**에서 하고, 사용자 행을 잠근다(`SELECT … FROM users WHERE id=:u FOR UPDATE`,
ADK 지출 `wallet_service.hold` 와 같은 방식). 잠근 뒤에 합계·개수를 다시 세서 한도를 넘으면 거절한다 →
12개가 동시에 와도 한도를 넘는 업로드가 끼어들지 못한다. 파일은 행을 확정(커밋)한 뒤에 디스크에 쓰고, 쓰기에 실패하면 행을 지운다
(행만 있고 파일이 없는 경우는 정리 작업이 지운다). 검증: PostgreSQL 에서 스레드 12개 동시 업로드 테스트(ADK 동시성 테스트와 같은 틀).

### 기존 파일
- 소유자를 알 수 없으므로 `uploads` 행을 만들지 않는다 → 한도 계산에서 제외, 이미 올라간 글의 사진은 그대로 보인다.
- 이 파일들의 고아 정리는 지금 스크립트(파일 시각 + 글 참조)로 계속한다.
- (선택) 기존 글·댓글의 `image_url` 을 훑어서 글쓴이를 소유자로 추정해 행을 채우는 백필 스크립트 — 글쓴이가 올린 게 거의 확실하지만
  남의 사진을 붙인 경우는 어긋날 수 있어서 선택 사항으로 둔다.

### 마이그레이션 계획
1. 새 테이블 `uploads` 는 시작할 때 `create_all` 로 자동 생성된다 (기존 테이블은 건드리지 않는다).
2. 배포 순서: ① 백엔드가 새 테이블을 만들고, 업로드 시 행을 기록하되 **한도는 켜지 않는다**(기록만) → ② 며칠 사용량을 보고 한도 값을 정한다 →
   ③ 설정으로 한도를 켠다. 프론트는 413 `UPLOAD_QUOTA_EXCEEDED` 메시지만 보여 주면 된다.
3. 롤백: 코드를 되돌려도 테이블은 남고 무해하다. 한도는 설정 하나로 끌 수 있다.
4. API 계약: 업로드 응답은 그대로(`image_url`). 새 오류 코드 `UPLOAD_QUOTA_EXCEEDED`(413) 하나만 추가된다.

### 위험
- "내가 올린 파일만 붙이기"는 기존 글을 **수정**할 때 예전 사진(소유자 행 없음)을 유지하는 경우를 허용해야 한다
  (수정 요청의 `image_url` 이 그 글의 현재 사진과 같으면 통과).
- 사진 크기: 큰 휴대폰 사진(12MP 이상)은 5MB 를 넘을 수 있어 올릴 수 없다 → 프론트에서 올리기 전에 줄이는 것을 권장(별도 FE 작업).
- 전체 디스크 한도는 앱이 아니라 볼륨 크기·모니터링으로 관리한다 (Docker 볼륨 용량 알림).

### 사진 저장 형식 (선택, 하지 않음)
DB에는 `/uploads/<이름>` 상대 경로만 저장하고 응답에서 `PUBLIC_BASE_URL`로 펼치는 안도 있어요. 도메인을 바꿔도 기존 글의 사진이 안 깨지는
장점이 있지만 **저장 데이터 형식이 바뀌어서** 지금은 하지 않았어요(현재는 `PUBLIC_BASE_URL`을 쓰는 절충).

## 4. pip-audit 결과 (실행함 — 2026-11-20)

격리된 임시 가상환경(`/tmp/pip-audit-env`)에 도구만 설치하고, 프로젝트 가상환경의 `pip freeze`(설치된 실제 버전 60개)를 `--no-deps`로
검사했어요. **프로젝트에는 잠금 파일이 없어서**(`pyproject.toml` 의 `>=` 범위뿐) 설치된 버전을 기준으로 했어요. 나간 정보는 패키지
이름·버전뿐이에요. 프로젝트 의존성·코드는 바꾸지 않았어요.

- **운영 이미지**: `Dockerfile` 이 `pip install .` 만 해서 **빌드할 때마다 가장 새 버전을 받아요**. 그래서 새로 빌드한 이미지는 위 패키지가 이미
  고쳐진 버전일 가능성이 높아요(지금 개발 PC 의 가상환경이 오래된 것). 다만 재현성이 없고 취약 버전이 섞일 수 있어요.
- **권장 (승인 필요, 주요 업그레이드 아님)**: ① 지금 가상환경에서 `pip install -U certifi pyasn1 opentelemetry-api` 후 테스트 ② 잠금 파일 도입
  (`pip-compile --generate-hashes` 로 `requirements.lock`, Dockerfile 은 잠금 파일로 설치) ③ CI 에 `pip-audit` 추가(주 1회·PR 마다).
